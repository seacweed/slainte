# Slainte 구현 계획

문서 버전: v2
작성 기준일: 2026-08-09
기준: 회의록, 개발 기획 PDF (3), 기획 아이템·레시피 CSV, 현재 프로젝트 코드와 자동 검증 결과

## 1. 목표

이 문서는 앞으로 구현할 기능의 순서, 책임 범위, 선행 자료, 완료 조건을 정리한다.

가장 먼저 영업 주문 흐름을 완성하고, 이후 액체 시각 품질과 콘텐츠 데이터를 확장한다. 주문 제조는 영업과 에피소드에서 같은 실행 엔진을 사용하되, 각 흐름의 노출 방식과 보상 정책은 분리한다.

## 2. 구현 원칙

- 주문 판정 로직을 영업용과 에피소드용으로 중복 구현하지 않는다.
- `BusinessOrderSessionController`를 공통 주문 세션 엔진으로 유지한다.
- 영업과 에피소드는 `OrderSessionRequest`로 주문 표시, 피드백, 보상 적용 여부를 전달한다.
- 화면에 보이는 정보와 내부 판정 데이터를 분리한다. 주문서에는 대사만 표시하고 레시피 ID, 술 종류, 가격은 노출하지 않는다.
- 진행 상태의 기준은 `GameProgress`로 통일한다.
- 레시피, 손님, 해금 조건, 색상은 코드에 직접 작성하지 않고 데이터로 관리한다.
- 확정되지 않은 얼음과 레시피 표시 방식은 인터페이스만 열어 두고 최종 시안 전에 과도하게 구현하지 않는다.

## 3. 현재 기준선

| 영역 | 상태 | 현재 내용 |
|---|---|---|
| 공통 주문 세션 | 구현됨 | 영업과 에피소드가 `BusinessOrderSessionController`를 공유 |
| 주문 상태 전환 | 구현됨 | 주문 제시, 자동 제조 진입, 잔 전진 제출, 피드백, 완료 처리 |
| 주문 판정 | 구현됨 | CSV 레시피와 주문 템플릿을 사용한 Good·Mid·Bad 판정 |
| 주문서 표시 | 구현됨 | 주문 대사만 표시하며 술 종류, 수량, 가격은 숨김 |
| 주문 조작 UI | 구현됨 | 별도 주문 버튼 없이 대사 종료 후 자동 수락하며, 잔을 앞으로 끌어 제출 |
| 손님 풀 | 구현됨·실데이터 필요 | `members` 목록 기반 1인·다인 방문, 조건·가중치·재등장 대기·주문 추첨·방문 이력 저장 |
| 판정 중 상단 문구 | 수정됨 | 계속 남아 있던 판정 문구 제거 |
| 젓기 | 구현됨·검증 필요 | 막대 도구인 `StirringRodController` 사용 |
| 셰이킹·스트레이너 | 구현됨·시각 검증 필요 | 스트레이너 일체형 코블러 셰이커가 왕복 흔들기 동작을 감지해 `Shake`를 기록 |
| 액체 온도 | 구현됨·검증 필요 | 액체 입자별 온도와 접촉에 따른 온도 평형 처리 |
| 김 | 구현됨·시각 검증 필요 | 뜨거운 표면 입자에서 발생하며 `water_particle` 스프라이트 재사용 |
| 액체 색상 | 수정됨·시각 검증 필요 | 입자 중심과 가장자리 색 차이 문제를 실제 플레이에서 재확인 필요 |
| 기획 CSV 임포트 | 구현됨 | 아이템·진열장·레시피 에셋을 ID 기준으로 갱신하고 빈 템플릿 행을 제외 |
| 기본 레시피 데이터 | 구현됨·일부 자료 필요 | CSV 18종 중 배합이 있는 15종 주문 가능, 커피 3종은 배합 대기 |
| 숨은 Mid 판정 | 구현됨 | 잔·얼음 변형 73종을 레시피북에서 숨긴 판정 에셋으로 생성 |
| 도수 계산 | 구현됨 | 명시 ABV가 없으면 재료별 `ABV × 용량`의 가중 평균으로 계산 |
| 전체 콘텐츠 데이터 | 진행 중 | 손님, 색상, 해금, 커피 3종 배합 데이터 추가 필요 |

## 4. 단계별 구현 계획

### 4.1 단계 1 — 주문 흐름 완성

우선순위: 최우선

#### 작업

- [x] 샘플 영업 주문 세 건의 연속 흐름을 검증한다.
  - 손님 등장
  - 주문 대사
  - 주문 자동 수락과 제조 진입
  - 잔을 앞으로 끌어 제출
  - 50/30 Good, 50/50 Mid, 빈 잔 Bad 피드백
  - 돈, 명성, 재고 반영
  - 영업 종료와 다음 날짜 진행
- [x] 에피소드 제조 노드가 같은 주문 세션과 잔 제출 제스처를 사용하는지 회귀 검증한다.
- [x] 에피소드 주문에서는 영업 보상과 영업 순서가 변하지 않는지 확인한다.
- [x] Good·Mid·Bad의 개별 판정, 돈·명성 보상, 누적 결과를 샘플 데이터로 검증한다.
- [ ] Good은 성공 분기, Mid와 Bad는 실패 분기로 연결되는 현재 규칙을 기획과 재확인한다.
- [x] 주문 거절, 주문 포기, 제조 중 버리기를 제공하지 않는다.
- [ ] 제출할 잔이 없거나 레시피 데이터를 찾지 못했을 때 복구 가능한 오류 처리를 확인한다.
- [x] 드래그 중인 잔이 전방 기준선을 넘을 때만 제출되도록 검증한다.
- [ ] 저장 후 재실행했을 때 돈, 명성, 재고, 영업 진행 위치가 유지되는지 확인한다.
- [ ] 손님별 주문 대사와 결과 대사를 실제 데이터로 교체한다.
- [x] 주문서에는 대사 외의 레시피명, 가격, 수량을 추가하지 않는다.

#### 구조 결정

영업과 에피소드의 공통 범위는 다음과 같다.

```text
주문 요청
→ 제조 세션 생성
→ 잔 내용 분석
→ 레시피 판정
→ Good·Mid·Bad 결과 생성
→ 호출한 흐름에 결과 반환
```

영업만 담당하는 범위는 손님 순서, 주문 대사 후 자동 제조 진입, 돈·명성 보상, 영업 진행도다. 에피소드만 담당하는 범위는 제조 노드 진입, 결과 분기, 에피소드 플래그와 변수 변경이다.

#### 완료 조건

- 영업 주문 3건 이상을 연속 처리해도 상태와 UI가 남지 않는다.
- 주문 대사가 끝나면 별도 버튼 없이 제조로 진입한다.
- 잔을 전방으로 끌었을 때만 제출되고, 주문 관련 조작 버튼은 표시되지 않는다.
- Good·Mid·Bad가 의도한 표정, 대사, 보상으로 연결된다.
- 에피소드 주문과 영업 주문이 서로의 진행도와 보상을 침범하지 않는다.
- 저장과 불러오기 후 재고 및 진행 상태가 일치한다.

### 4.2 단계 2 — 손님 표시와 주문 데이터 확장

우선순위: 주문 흐름 완료 직후

#### 작업

- [x] 캐릭터 표시 구성, 방문 단위, 주문 데이터를 분리해 한 캐릭터가 여러 주문을 가질 수 있게 한다.
- [x] 주문 데이터에 주문 대사, Good·Mid·Bad 결과 대사, 내부 레시피 ID를 연결한다.
- [ ] 손님은 기본적으로 Mid 스프라이트로 등장한다.
- [ ] 제조 중 Mid 상태에서 눈 깜박임 애니메이션을 재생한다.
- [ ] 눈이 없는 캐릭터는 깜박임 프레임을 지정하지 않으면 애니메이션을 생성하지 않는다.
- [ ] Good과 Bad는 순간 결과 연출이므로 눈 깜박임을 넣지 않는다.
- [x] 방문과 주문별 등장 조건을 플래그, 변수, 날짜, 완료 에피소드 조합으로 표현한다.
- [x] 특수 인물은 에피소드 조건에 따라 영업 등장 후보에 포함하거나 제외한다.
- [x] 같은 날짜와 저장 상태에서는 같은 결과가 나오도록 가중치 추첨을 결정론적으로 처리한다.
- [x] 방문 완료 날짜와 누적 횟수를 저장하고 재등장 대기 일수를 적용한다.
- [ ] 실제 손님·주문·등장 조건 데이터로 샘플 풀을 교체한다.

#### 권장 데이터 관계

```text
CharacterData
  └─ 스프라이트, 표정, 눈 깜박임

CustomerVisitData
  ├─ visitKey
  ├─ members[]                 (인원수 제한 없는 등장 구성)
  ├─ condition                 (날짜·플래그·변수·선행 에피소드)
  ├─ weight / cooldownDays
  └─ orders[]                  (조건과 가중치를 가진 주문 후보)

CustomerOrderData
  ├─ requestedRecipeId
  ├─ orderType
  ├─ lines
  └─ feedbackLinesGood/Mid/Bad
```

커플과 단체는 별도 유형으로 나누지 않는다. 두 명이면 `members`가 두 개인 방문, 세 명 이상이면 그만큼 구성원이 있는 방문이다. `tags`는 검색·연출용 보조 정보이며 런타임 분기 기준으로 사용하지 않는다.

#### 완료 조건

- 같은 캐릭터에게 주문을 추가해도 캐릭터 원본 데이터를 수정할 필요가 없다.
- 눈 깜박임 지원 여부가 캐릭터별 데이터만으로 결정된다.
- 특수 인물의 등장 여부를 코드 변경 없이 조건 데이터로 조정할 수 있다.

### 4.3 단계 3 — 액체, 온도, 김 시각 품질 검증

우선순위: 주문 회귀 검증과 병행 가능

#### 작업

- [ ] 액체 입자 중심과 가장자리 색이 다른 현상을 네 가지 잔과 여러 색상에서 재검증한다.
- [ ] 메타볼 경계값, 입자 스프라이트 알파, 재질 혼합 방식 중 원인을 확정한다.
- [ ] 액체가 섞일 때 중심과 가장자리의 색조가 동일하게 유지되는지 확인한다.
- [ ] 김이 실제로 잔 내부의 뜨거운 표면 입자 위치에서 시작하는지 확인한다.
- [ ] 평균 온도가 아니라 표면 입자의 온도와 부피 가중 강도로 발생량이 변하는 현재 방식을 검증한다.
- [ ] 55℃ 이상에서 시작하고 48℃ 아래에서 멈추는 기준을 플레이 감각에 맞게 조정한다.
- [ ] 데이브 더 다이버의 녹차처럼 둥근 김 덩어리가 적은 수로 상승하고 짧게 사라지는지 확인한다.
- [ ] 김이 액체용 `water_particle` 스프라이트를 사용하며 별도 이미지가 필요 없는지 최종 승인한다.
- [ ] 입자 속도 X·Y·Z 곡선 방식을 통일한 수정이 실행 중 경고를 발생시키지 않는지 확인한다.

#### 완료 조건

- 빨강, 파랑, 노랑, 투명 계열에서 액체 가장자리 색이 튀지 않는다.
- 차가운 액체에서는 김이 발생하지 않는다.
- 뜨거운 액체가 식으면 김의 발생량이 줄어들다가 자연스럽게 멈춘다.
- 잔을 이동하거나 기울여도 김의 시작 위치가 액체 표면을 따라간다.
- Unity 콘솔에 입자 곡선 관련 경고가 발생하지 않는다.

### 4.4 단계 4 — 재료, 레시피, 색상, 잔 데이터 완성

우선순위: 주문 시스템 승인 후

#### 작업

- [x] 제공된 아이템 CSV의 유효 아이템 15종을 `ItemDef`와 `LiquorBottleDef`로 변환한다.
- [x] 레시피 CSV 18종을 `CocktailRecipeDef`로 변환한다.
- [x] PDF 배합이 확정된 15종을 주문 가능 레시피로 연결한다.
- [x] 네 가지 잔과 얼음 유무 조합을 숨은 Mid 판정 레시피 73종으로 생성한다. 제조법·재료 변형은 생성하지 않는다.
- [x] CSV를 다시 임포트해도 같은 ID 에셋을 갱신하고 중복 생성하지 않게 한다.
- [x] 빈 템플릿 행과 `임시 비워둠` 행을 임포트에서 제외한다.
- [x] 레시피 도수를 재료별 도수와 사용 용량으로 계산한다.
- [ ] 아이리시 커피, 블랙 커피, 핫 테디의 정확한 재료 ID와 용량을 받아 주문 가능으로 전환한다.
- [ ] 칵테일 12종의 기본 색상 데이터를 추가한다.
- [ ] Mid 변형을 포함한 최대 84종 색상 매핑을 데이터로 관리한다.
- [ ] 니트와 온더락 8종의 색상 데이터를 추가한다.
- [ ] 기획에서 전달받은 RGBA 값을 단일 색상 테이블로 정리한다.
- [ ] 원본 이미지에서 색이 바뀌는 부분만 마스크로 분리하고 에디터에서 색상 필터를 적용하는 방식을 시험한다.
- [ ] 얼음은 액체 색상 필터의 영향을 받지 않도록 별도 레이어로 분리한다.
- [x] 네 종류 잔의 판정 ID(`rock`, `highball`, `hurricane`, `martini`)를 등록한다.
- [ ] 네 종류 잔의 최종 스프라이트, 충돌 형태, 용량을 확정한다.
- [ ] 레시피 해금 출처를 에피소드와 레시피북으로 구분한다.
- [ ] 해금 후에는 하나의 레시피 스프라이트를 재사용하고 표시 상태만 바꾼다.
- [ ] 레시피는 영업뿐 아니라 휴식 중에도 열람 가능하게 한다.
- [ ] 레시피북 소분류에 지정 색상을 적용한다.

#### 권장 해금 데이터

```text
RecipeUnlockRule
  ├─ recipeId
  ├─ sourceType: Episode | RecipeBook | Default
  ├─ sourceId
  └─ conditions
```

#### 완료 조건

- 레시피 CSV에 존재하는 모든 재료 ID가 실제 아이템 데이터와 연결된다.
- 누락된 RGBA, 잔, 레시피 참조를 에디터 검증 메뉴에서 한 번에 찾을 수 있다.
- 색상 변경을 위해 칵테일별 완성 이미지를 별도로 만들 필요가 없다.
- 해금 출처와 관계없이 동일한 레시피가 중복 등록되지 않는다.

### 4.5 단계 5 — 재고 표시

#### 작업

- [ ] 재고 잔량용 이미지 10종의 정확한 구간 매핑을 확정한다.
- [ ] 가득 찬 상태에는 `full` 이미지를 사용한다.
- [ ] 나머지 상태는 실제 잔량의 앞자리 또는 백분율 구간에 따라 이미지를 선택한다.
- [ ] 사용하지 않는 10번 이미지를 데이터에서 제외한다.
- [ ] 재고 이미지는 우선 불투명도 80%로 표시한다.
- [ ] 병 한 개의 현재 잔량과 전체 보유 병 수를 구분해서 보여 준다.

#### 완료 조건

- 경계값에서 이미지가 앞뒤로 반복 변경되지 않는다.
- 구매, 제조, 제출, 저장·불러오기 후 표시와 실제 재고가 일치한다.

### 4.6 단계 6 — 다인 손님과 특수 등장

- [x] 손님 방문과 에피소드가 같은 진행 조건 평가기를 사용한다.
- [ ] 발렌티노와 베리를 구성원 두 명인 실제 방문 에셋으로 등록한다.

#### 완료 조건

- 새로운 1인·커플·단체 방문을 추가할 때 전용 코드를 작성하지 않는다.
- 선택 분기 이후 잘못된 캐릭터가 화면에 남지 않는다.
- 등장 조건을 데이터에서 읽고 설명할 수 있다.

### 4.7 단계 7 — 에피소드 보드 조건 확장

- 모든 잠금 및 선택 불가 상태에 데이터 기반 사유가 존재한다.
- 메인 퀘스트가 일반 에피소드 슬롯 갱신으로 사라지지 않는다.

7. 재고 이미지 10종과 잔량 구간 매핑표

## 7. 바로 다음 작업

다음 구현 단위는 샘플 손님 풀을 실제 데이터로 교체하는 작업이다. 손님별 캐릭터 ID, 함께 등장하는 구성원과 슬롯, 주문 대사, 결과 대사, 내부 레시피 ID, 등장 조건을 받으면 `CustomerVisitData`와 `CustomerOrderData`로 등록한다. 그다음 여러 날 영업을 반복해 조건 필터, 재등장 대기, 저장·불러오기, 1인·다인 표시를 플레이 검증한다. 동시에 생성된 15종 레시피의 Good과 대표 Mid 변형도 실제 제조로 확인한다.
